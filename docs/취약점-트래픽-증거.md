# 취약점 다중 트래픽 증거

취약점 상세의 「연관 트래픽」은 페이지 간 다중 선택, 용도 및 설명, 정렬, 바인딩 해제를 지원한다. 트래픽 페이지에서도 레코드를 다중 선택해, 한 번에 기존 취약점 하나에 연결할 수 있다. 작업이 상속한 취약점 증거는 읽기 전용이며, 수정하려면 원본 작업으로 들어가야 한다.

시스템 설정의 「Agent 트래픽 자동 바인딩」은 기본적으로 꺼져 있으며, 조회 및 수정 인터페이스는 `/api/settings` 의 `agent_traffic_binding` 이다. 켜면 요청/응답, 도구 호출 및 프롬프트 열람에 따른 토큰 소비가 늘어난다; 다음 라운드 Agent부터 새 설정이 적용된다. 꺼져 있을 때는 자동 바인딩 파라미터와 보충 바인딩 도구를 숨기고, 자동 바인딩 안내를 주입하지 않으며, 이미 실행 중인 세션에서 새로 제출되는 자동 바인딩을 거부한다. 수동 바인딩, 트래픽 캡처, 저장된 증거 읽기 및 내보내기는 영향받지 않는다.

켜져 있을 때 기본 흐름은 「발견이 저장됨 → 보고 Agent가 자동으로 트리거됨 → 트래픽을 확인하고 바인딩 → 최신 증거 버전으로 보고서 작성」이다. 보고자는 `evidence` 에 검증 명령, 주요 출력, 기존 실제 트래픽 ID 및 용도를 남긴다; 보고 Agent는 취약점 상세와 실행 기록을 바탕으로 `traffic_search` / `traffic_get` 으로 확인한 뒤 `bind_finding_traffic` 을 호출하고, 다시 최신 `version` 을 읽어 보고서를 저장한다. 스위치를 끈 경우 보고 Agent는 원본 트래픽 검색/읽기 도구를 추가로 얻지 않으며 자동 바인딩도 하지 않는다; 다만 수동으로 바인딩된 스냅샷은 계속 읽어 보고서를 생성할 수 있다.

기존 호출자와의 호환: `report_finding` 의 `traffic_refs` / `evidence_hint_id` 는 여전히 명시적인 즉시 바인딩에 사용할 수 있다. 바인딩은 선택 사항이다: TCP 등 HTTP가 아닌 취약점, 캡처되지 않았거나 정확한 레코드를 찾을 수 없는 경우에는 참조를 생략해도 정상적으로 보고 및 보고서 작성이 가능하다; 명령 출력, 로그 등 다른 검증 가능한 증거를 남기고, 바인딩하지 않은 이유를 설명하는 것을 권장하며, 필수 필드를 새로 추가하지는 않는다. 제출한 ID는 전부 유효하고 본문이 완전해야 한다. 하나라도 실패하면 이번 바인딩 작업 전체가 롤백된다; 상보와 함께 명시적으로 바인딩이 실패하면 이번 상보 전체가 롤백된다. 같은 스냅샷을 중복으로 추가해도 바인딩이 늘어나지 않고 설명도 덮어쓰지 않는다.

## Agent 번호와 보고서 버전

`report_finding` 에 선택적 파라미터가 추가되었으며, 배열 순서가 곧 초기 증거 순서다:

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 트래픽 ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "다른 실제 트래픽 ID", "role": "proof", "note": "재현 요청"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 증명), `verification`(보충 검증), `supporting`(보조 증거, 기본값)이다. 먼저 `traffic_search` / `traffic_get` 으로 실제 레코드를 확인한다; 도메인과 시간은 후보를 좁히는 데만 쓰이며 작업 소속을 추정하는 데 쓰이지 않는다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 안내](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)를 참고했으며, 이 프로젝트의 선택적 바인딩 규칙과 결합해 바인딩하지 않은 이유에 대한 필수 검증을 도입하지 않았다. ID를 추측해서는 안 되며, 바인딩을 보충하기 위해서만 중복으로 탐지해서도 안 된다.

반환의 첫 줄은 여전히 `finding recorded: <탐색 노드 ID>` 이다; 이어지는 JSON에는 독립된 취약점 레코드의 `finding_id`, 탐색 노드 `finding_node_id`, 바인딩 요약이 담긴다.

- `get_finding_traffic(finding_id)` 는 **독립된 취약점 레코드 ID**를 사용하며, 정렬된 목록과 `version` 을 반환한다; `binding_id`, `side=request|response`, `offset`, `length` 를 전달하면 구간별로 읽을 수 있고, 구간당 최대 8192바이트다.
- `update_finding_report` 의 `finding_id` 는 **여전히 탐색 노드 ID를 사용**한다. `evidence_version` 이 추가되어 실제로 읽은 버전을 채운다; 생성 중에 증거가 변경되면 이전 버전으로의 쓰기를 거부하므로, 다시 읽고 재생성해야 한다.
- 버전을 전달하지 않은 기존 보고서 호출은 기존 트래픽 증거를 덮어쓴다고 간주하지 않는다. 바인딩, 설명, 용도 또는 정렬이 바뀌면 기존 보고서에 업데이트 필요 알림이 표시된다.

자동 바인딩을 켜면 `add_hint` / `add_task_hint` 는 단일 힌트나 배치 `hints` 의 각 요소에 `traffic_refs` 를 저장하는 것을 지원한다. Planner가 대신 보고할 때는 `evidence_hint_id` 를 전달해, 해당 작업의 힌트에 있는 참조임을 명확히 지정할 수 있으며, 상속된 힌트는 참조할 수 없다. 시스템은 도메인, 시간 또는 열람 기록으로 바인딩을 추측하지 않는다. 제출이 실패하면 부분적인 취약점이 생성되거나 보고서가 미리 트리거되지 않는다.

기존 취약점에 바인딩이 빠졌을 때는 `bind_finding_traffic(finding_id, traffic_refs)` 로 보충할 수 있으며, 중복 등록이 필요 없다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` 은 명확한 `finding_id` 와 `finding_node_id` 를 반환한다; 기존 `id` 는 탐색 노드의 의미를 유지한다.

시작 시 기존 도구 schema에 선택적 속성만 추가하며, 기본 트래픽 도구 바인딩을 보고 Agent로 확장한다; 보충 바인딩 도구는 기본적으로 보고 Agent에 맡긴다. 커스텀 바인딩 목록, 프롬프트, 설명 및 활성화 상태는 유지된다. 안내는 최종 도구 조립이 끝난 뒤 통일되게 추가된다: 보고 역할은 기존 증거를 인계하는 일을 담당하고, 보고 Agent는 확인, 바인딩, 보고서 작성을 담당한다. 플랫폼 대화에 작업 컨텍스트가 없을 때는 구조화된 힌트를 통해 작업 Agent에게 인계해야 하며, 직접 보고해서는 안 된다. 작업 완료를 판정하기 전에 먼저 기존 증거를 인계해야 한다; 바인딩이 없다고 해서 강제로 기다릴 필요는 없다. 실패한 `report_finding` 은 보고 Agent를 트리거하지 않는다.

## API

기본 경로: `/api/exploration/findings/{finding_id}/traffic`, 독립된 취약점 ID를 사용한다. 인증은 기존 방식을 따른다; `context_task` 가 작업 가시성 및 상속 읽기 전용 여부를 검증한다.

| 메서드 / 상대 경로 | 요청 / 응답 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서가 채택한 버전 |
| `POST` | `{"traffic_refs":[...]}` 일괄 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 반드시 전체 목록이어야 함 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 길이 제한이 있는 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1` 로 전체 원본 바이트 다운로드 |

버전/정렬 세트 충돌, 아카이브 중 쓰기는 `409`; 상속된 쓰기는 `403`; 존재하지 않거나 해당 취약점에 속하지 않는 바인딩은 `404`; 트래픽/첨부파일 읽기 및 검증 실패는 명확한 오류를 반환한다.

## 저장과 마이그레이션

시작 시 PostgreSQL에 멱등하게 마이그레이션한다: `traffic_evidence_snapshots`, `finding_traffic_bindings`, 그리고 `findings.evidence_version` / `report_evidence_version`(기본값 0)이 추가된다. 과거 텍스트로 보충 바인딩을 추측하지 않는다.

스냅샷은 원본 트래픽 ID, 캡처 시간, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이와 SHA-256을 보존한다. 본문은 해시 기준으로 `<data>/evidence/blobs/<앞 두 자리>/<hash>.bin` 에 저장되며, 정리 대상인 `data/traffic` 과는 독립적이고, 여러 취약점이 스냅샷/본문을 공유할 수 있다. 스냅샷은 내용 수정 인터페이스를 제공하지 않으며, 검증 불일치 시 읽기와 내보내기가 실패한다.

원본 트래픽의 쓰기 락 하에서 전체 본문을 읽는다. 대용량 본문 blob과 과거 디렉터리 레코드를 포함한다. 먼저 파일을 영속화하고 검증한 뒤, 단일 PostgreSQL 트랜잭션으로 탐색 노드, 의도 관계, 취약점, 스냅샷, 바인딩을 쓴다; 커밋 후에야 플래너에게 통지한다. 실패 시 참조 없는 파일이 남을 수 있지만, 부분적인 비즈니스 레코드는 생기지 않는다.

PostgreSQL advisory lock `7337741004` 가 증거 파일과 SQL 참조를 조율한다; 작업 행 락은 아카이브 대기열에 들어간 뒤의 증거 수정을 금지한다. 복구는 본문 설치부터 메타데이터 커밋까지 전 과정에서 증거 락을 유지한다. 취약점 삭제는 바인딩을 연쇄적으로 제거한다.

정리기는 매시간 실행되며, 참조가 없고 진행 중인 작업이 아닌 것만 회수하고, 최소 24시간 지연된다. 일반 트래픽 정리는 증거 디렉터리를 건드리지 않는다. 핫 데이터를 백업할 때는 PostgreSQL과 `data/evidence` 를 함께 백업한다.

## 내보내기와 아카이브

Markdown에는 정렬된 증거 목록과 버전이 포함된다; JSON에는 메타데이터가 포함된다; CSV에는 개수와 바인딩 ID가 추가된다. `md-zip` 은 취약점 Markdown을 보존하며, 다음을 제공한다:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 메시지를 참조한다. 다운로드를 보내기 전에 첨부파일 복사, 해시 검증, 압축, 디스크 동기화 및 모든 ZIP 항목의 CRC 읽기 검증을 완료한다; 누락/손상 시 전체 다운로드가 실패한다. 완전한 첨부파일은 원본 바이너리 그대로 보존된다.

아카이브 v3은 취약점 바인딩 관계를 기준으로 스냅샷과 본문을 모으며, 원본 트래픽이나 도메인에 의존하지 않는다. 패키지 검증이 끝난 뒤에야 핫 데이터를 정리한다; 공유 증거는 계속 보존된다. 복구는 먼저 설치된 본문을 검증한 뒤, 트랜잭션으로 메타데이터와 바인딩을 복구하며, 실패 시 재시도를 지원한다. v1/v2도 계속 복구 가능하며, 누락된 새 필드는 명시적으로 0으로 채운다.

## 검증과 경계

각 테스트 패키지마다 독립적인 새 PostgreSQL 테스트 데이터베이스를 `ARTEX_PG_DSN` 으로 지정해 설정하며, 남아 있는 작업/모델 픽스처가 백그라운드 실행을 유발하는 것을 피한다. 관련 패키지의 전체 테스트를 실행하고, 설정 누락으로 인한 스킵이 없는지 확인한다:

```sh
# 각 패키지 실행 전 ARTEX_PG_DSN을 해당하는 독립 테스트 데이터베이스로 설정한다; 명시적 설정이 실패하면 반드시 에러가 나야 한다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증은 `npx tsc --noEmit`, 영향받은 파일의 Biome 검사, Webpack 빌드, `NEXT_EXPORT=1` 정적 내보내기를 포함한다. 독립된 캐시 디렉터리를 사용해 실행 중인 개발 서버를 덮어쓰지 않도록 한다.

로컬 환경의 end-to-end 검수는 독립된 포트, 통제된 HTTP / 도메인 HTTPS 타깃, 임시 데이터 디렉터리를 사용하며, 두 가지 바인딩 진입점, 페이지 간 선택, 정렬/설명, 오류 안내, 상속 읽기 전용, 다운로드, 그리고 원본 트래픽 삭제 후의 내보내기, 아카이브, 핫 본문 회수, 복구 및 해시 검증을 포괄한다.

첫 버전은 전역 증거 조율 락을 사용한다; 대량 바인딩/내보내기나 느린 첨부파일 다운로드 중에는 다른 증거 작업이 대기할 수 있다. 녹화 레코드나 완전한 본문이 없을 때는 증거를 임의로 만들어낼 수 없다. 이 기능은 캡처 스위치를 변경하지 않으며, HTTPS로 IP에 직접 접근할 때의 인증서 문제도 다루지 않는다.
