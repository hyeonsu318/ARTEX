# 사이드 질문의 긴 대화와 컨텍스트 예산

2026-09-11 수정. 기존 구현은 요청 JSON의 글자 수를 그대로 token으로 간주했고 메인 작업의 32K 출력 예약까지 물려받았기 때문에, HTML, JS, 도구 결과가 많으면 정상적인 사이드 질문도 미리 거부했다.

## 오픈소스 구현 대조

- [Grok CLI 사이드 컨텍스트](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739): 최근의 사용자/어시스턴트 텍스트에서 조각을 발췌하며, 글자 예산은 약 2000이고 항목당 최대 400자까지 자른다. 이 경로에서는 연속된 사이드 질문 답변 기록을 유지하지 않는다.
- [Grok CLI 독립 요청](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts): 독립된 취소 신호; 모델이 지원하면 출력 상한은 2048 tokens; 도구를 제공하지 않는다.
- [Grok CLI 메인 세션 압축](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts): token을 추정하고, 최근 내용을 유지하며, 새 내용을 이전 요약에 갱신해 넣고, 턴을 넘나드는 절단을 처리한다.
- [OpenCode 세션 압축](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts): 전체 요청 추정, 출력/버퍼 예약, 최근 내용 + 롤링 요약, 도구 없는 요약 요청; 이 구현의 기본값은 최근 예산 8000, 요약 출력 상한 4096 tokens이다.
- [OpenCode 오버플로 복구](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts): 어시스턴트 출력이 아직 시작되지 않았을 때만 오버플로 복구를 시도하며, 복구 후의 호출은 같은 오버플로 복구 경로로 다시 들어가지 않는다.

ARTEX는 독립된 출력 예산, 최근 내용과 롤링 요약, 제한적인 복구 방식을 차용했다. norma v0.3.6의 구조화된 메시지와 도구 짝을 유지하며, Grok의 텍스트 발췌 방식은 그대로 가져오지 않았다; OpenCode의 메인 세션 압축 이벤트는 ARTEX 메인 transcript에 기록하지 않는다.

## 요청 예산과 실행

- 메시지는 norma의 콘텐츠 블록 단위 UTF-8 바이트 추정과 4/3 여유를 그대로 쓰며, 시스템 프롬프트, 도구 schema, 메시지 포장 오버헤드를 추가로 계산한다. 추정은 모델의 정확한 token 계산이 아니다.
- 사이드 질문의 출력은 기본적으로 최대 8192 tokens이며, 메인 설정에 이미 지정된 출력 상한도 넘지 않는다. 서비스 환경 변수 `ARTEX_BTW_MAX_OUTPUT_TOKENS`로 256–32768 범위의 상한을 설정할 수 있다; 제품 기본 모델이나 메인 작업 파라미터는 바꾸지 않는다.
- 입력 예산은 컨텍스트 윈도우에서 출력 상한과 안전 여유를 뺀 값이다; 윈도우를 알 수 없으면 플랫폼 기본값 200K를 쓴다. 안전 여유는 윈도우의 5%이며 최소 128, 최대 8192 tokens이다.
- 성공한 질의응답은 증가하는 일련번호 순으로 한 번에 최대 20쌍씩 불러온다. 원문은 최대 20쌍까지 유지하며, 그 token 예산은 입력 예산의 최대 1/4이고 16K를 넘지 않는다.
- 초과분의 질의응답은 롤링 요약에 갱신해 넣는다. 요약에는 과거 출처와 컨텍스트 시각이 붙으며, 과거 어시스턴트 답변은 새 도구 증거와 같지 않고 충돌 시 최신 메인 스냅샷을 우선한다.
- 메인 컨텍스트가 여전히 길면 사본 속의 오래된 메시지만 요약하고, 최근 부분은 최대 8K tokens까지 유지한다; 절단 지점은 도구 호출과 결과를 쪼개지 않는다. 지나치게 큰 단일 묶음은 통째로 요약에 들어간다.
- 요약 입력은 실제 남은 윈도우에 맞춰 UTF-8 안전하게 분할하며, 출력 상한은 2048 tokens이다; 빈 요약, 절단, 도구 호출, 요약 예산 초과는 캐시에 기록하지 않는다. 한 번의 사이드 질문은 최대 12번의 요약 호출을 할 수 있고 같은 120초 타임아웃의 제한을 받으며, 상한에 도달하면 명확하게 실패하고 무한 루프에 빠지지 않는다.
- 모델이 처음에 컨텍스트 초과를 반환했고 아직 텍스트나 도구 호출을 출력하지 않았다면, 더 줄인 뒤 최대 한 번 재시도한다; 추정 크기가 줄어들지 않으면 즉시 복구를 중단한다. 그 밖의 모델 오류와 부분 스트리밍 출력은 이 복구를 유발하지 않는다.
- 요약, 실패한 시도, 취소 시의 사용량을 포함해 확보한 모든 사용량은 같은 사이드 요청에 누적된다. Provider가 사용량을 반환하지 않으면 여전히 0만 기록할 수 있으며, 추정치를 실제 사용량인 것처럼 위장할 수 없다.

## 영속화와 화면

`side_question_sessions.memory`는 오래된 질의응답 요약, 포괄하는 ordinal, 그리고 스냅샷 신원별로 캐시된 메인 컨텍스트 요약을 저장한다. `side_question_requests.context_info`는 준비 단계, 실제로 재생한 묶음 수, 요약 사용 여부, 예산 추정을 저장한다.

요약은 원래 요청이 아직 실행 중이고 정리 버전이 일치할 때만 저장한다; 비우면 캐시도 함께 지워지며, 늦게 도착한 쓰기가 이미 정리된 데이터를 되살리지 않는다. 새 스냅샷은 이전 스냅샷의 요약을 재사용하지 않는다. 요약 필드는 v3 작업 아카이브와 함께 저장되며, 오래된 v3에서 필드가 없으면 빈 객체로 채우고, v1/v2도 계속 호환된다.

POST는 먼저 요청을 받아들여 반환하고, 준비와 압축은 백그라운드에서 수행하며 접수 잠금이나 데이터베이스 트랜잭션을 잡지 않는다. SSE/기록에는 준비, 질의응답 정리, 사본 압축, 답변 단계가 표시된다; 압축 실패는 해당 사이드 요청의 실패 종료 상태로 저장된다. 프런트엔드는 에러를 유지하고 이번에 실패한 질문의 초안을 복원하며, 떠 있는 알림으로 입력창을 가리지 않는다; 기록 폴링이 제출 에러를 더 이상 지우지 않는다.

## 검증 기록

- 19/20/21/50쌍 재생, 20쌍을 넘는 과거 결론 유지, 요약 캐시의 재시작 후 재사용: 자동화 통과.
- 매우 긴 다국어 답변과 코드 컨텍스트, 분할 요청 예산, 도구 짝, 스냅샷 불변, 새 스냅샷의 캐시 무효화: 자동화 통과.
- 요약 실패/취소/절단/초과/도구 반환, 비우기 경쟁, 호출 상한, 오버플로 복구는 한 번만, 부분 스트림은 재시도하지 않음: 자동화 통과.
- 독립 PostgreSQL에서의 페이지 분할, 재시작, v1/v2/v3 아카이브, 요약 캐시와 예산 메타데이터의 아카이브 복구, 새 필드가 없는 오래된 v3, 20개 부모 세션이 네 개의 동시성 슬롯을 공유하는 경우: 통과.
- Go 후보 서비스 빌드, 프런트엔드 TypeScript 검사, 수정한 컴포넌트의 Biome 검사, 독립 디렉터리에서의 Next.js 프로덕션 빌드: 통과.
- 내장 브라우저에서 독립된 UI 픽스처로 1280×720과 390×844에서 정리 단계, 요약 범위 안내, 실패 후 초안 복원, 떠 있는 에러 알림 없음, 가로 넘침 없음, 콘솔 에러 없음을 검증했다. 임시 픽스처는 제거했다.
- 로컬에 있는 Worker 스냅샷을 읽기 전용으로 재생했을 때 새 예산 검사를 통과했다; 예를 들어 Worker #3의 293085자 스냅샷은 더 이상 로컬 글자 수 계산 때문에 잘못 거부되지 않는다. 이 항목에는 외부 모델 호출이 없다.
- 이번에 비공개 Worker 스냅샷을 Grok에 보내는 실제 대화 테스트는 자동 승인 검토에서 거부되어 실행되지 않았으며, 통과 항목으로 치지 않는다.
- 2026-09-11 00:37 사용자 요청에 따라 로컬 백엔드를 재시작했으며, 기존 데이터베이스, 데이터 디렉터리, 로그인 설정을 그대로 썼다. 실행 파일과 후보 바이너리의 SHA-256이 일치하며, 백엔드와 프런트엔드 프록시의 `/api/health`가 모두 정상을 반환했다.
